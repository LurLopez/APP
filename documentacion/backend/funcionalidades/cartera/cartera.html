Cartera de inversión (portfolio) — Backend

Compras/ventas con cantidad, precio y fecha; reconstrucción FIFO; dividendos estimados por fecha de pago real; valoración y alocaciones por empresa y sector.

✓ Implementado y probado · 2026-08-17

Qué hace

El backend guarda cada operación (compra o venta con cantidad, precio y fecha) en portfolio_transactions y reconstruye el estado de la cartera en cada lectura: lotes FIFO, coste medio, valor actual con la cotización de Yahoo, ganancias no realizadas y realizadas (con y sin dividendos), dividendos acumulados estimados con las fechas de pago reales, dividendos anuales previstos (TTM) y distribución por empresa y por sector.

Base de datos

CREATE TABLE portfolio_transactions (
    id           SERIAL PRIMARY KEY,
    user_id      INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    ticker       TEXT NOT NULL,
    company_name TEXT NOT NULL,
    type         TEXT NOT NULL CHECK (type IN ('buy', 'sell')),
    shares       NUMERIC(18, 6) NOT NULL CHECK (shares > 0),
    price        NUMERIC(18, 6) NOT NULL CHECK (price >= 0),
    trade_date   DATE NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

No hay tabla de cartera: el estado se reconstruye de las transacciones. Índices por (user_id, trade_date, id) y (ticker).

Pestañas y grupos

Jerarquía pestaña → grupo → miembros con 4 tablas nuevas (todas con ON DELETE CASCADE):

CREATE TABLE portfolio_tabs (
    id SERIAL PRIMARY KEY, user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name TEXT NOT NULL, color TEXT NOT NULL DEFAULT '#2563eb',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(), UNIQUE (user_id, name)
);
CREATE TABLE portfolio_groups (
    id SERIAL PRIMARY KEY, user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    tab_id INT NOT NULL REFERENCES portfolio_tabs(id) ON DELETE CASCADE,
    name TEXT NOT NULL, color TEXT NOT NULL DEFAULT '#2563eb',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(), UNIQUE (user_id, tab_id, name)
);
CREATE TABLE portfolio_group_rules (
    id SERIAL PRIMARY KEY, user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    group_id INT NOT NULL REFERENCES portfolio_groups(id) ON DELETE CASCADE,
    ticker TEXT NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT now(), UNIQUE (group_id, ticker)
);
CREATE TABLE portfolio_group_lots (
    id SERIAL PRIMARY KEY, user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    group_id INT NOT NULL REFERENCES portfolio_groups(id) ON DELETE CASCADE,
    buy_transaction_id INT NOT NULL REFERENCES portfolio_transactions(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(), UNIQUE (group_id, buy_transaction_id)
);
  • Regla de ticker (portfolio_group_rules): marcar "toda la acción" hace que las operaciones futuras de ese ticker entren solas en el grupo.
  • Sublínea (portfolio_group_lots): asignación de un lote concreto por buy_transaction_id (la compra debe ser del usuario → si no, 400 INVALID_LOT).
  • Un ticker/lote puede pertenecer a varios grupos; nombre duplicado de pestaña/grupo → 400 DUPLICATE.
  • GET /api/portfolio adjunta a cada posición sus grupos por regla (viaRule: true), a cada lote la unión de reglas + asignaciones explícitas (deduplicadas), y devuelve tabs y groups de nivel superior con ruleTickers y lotTransactionIds.

Cálculo FIFO

  • Los lotes son las compras ordenadas por fecha; cada venta consume los lotes más antiguos primero (FIFO, estándar de brokers).
  • La ganancia bruta de cada venta = Σ (precio venta − precio lote) × acciones, guardada por id de venta (realizedGain).
  • Venta sin respaldo → 400 NOT_ENOUGH_SHARES; borrar una compra que rompe el FIFO → 400 INVALID_STATE.

Dividendos y sector

  • Dividendos: histórico real de Yahoo por tramos de 5 años (Yahoo trunca con range=max), desde la compra más antigua; porción por lote (compra→venta para lo vendido, compra→hoy para lo que queda).
  • Anuales previstos: TTM (últimos 12 meses) por acción × acciones en cartera; yield = previstos / valor total.
  • Sector: SIC de EDGAR → sector amplio en español (ej. "Consumo defensivo", "Alimentación y bebidas"); "Otros" si no hay.
  • Fallo de Yahoo/EDGAR → posición con price: null/sector: null (no rompe la cartera).

Decisiones

  • FIFO (no FILO): estándar en brokers (IBRK); el usuario confirmó FIFO.
  • Sin comisiones: simplicidad en beta.
  • Una única cartera por usuario: decisión de producto.
  • Estado reconstruido de las transacciones: sin redundancia; siempre consistente por definición.
  • Regla vs sublínea: "toda la acción" es regla de ticker (las futuras entran solas); marcar sublíneas solo asigna ese lote.
  • Borrado en cascada y nombres únicos por usuario/pestaña (error DUPLICATE claro).

Pruebas

  • Ejemplo TAP del usuario: 50 compradas a 50 $, 20 vendidas a 60 $ → realizada 200 $; dividendos 28,8 $ (en cartera) + 19,2 $ (vendidas).
  • FIFO multi-lote: AAPL 10@100 + 10@150, venta 15@200 → quedan 5@150, realizada 1.250 $.
